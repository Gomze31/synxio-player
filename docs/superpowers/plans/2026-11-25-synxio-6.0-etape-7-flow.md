# Synxio 6.0 — Étape 7 : Mode Flow — Plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** La file d'attente peut être réordonnée d'un geste pour que chaque titre enchaîne sur le précédent par tempo (à l'octave près), tonalité compatible (roue de Camelot) et énergie voisine ; le lecteur dit pourquoi le titre suivant vient là ; un mix « Flow du jour » applique le même moteur à ce que l'utilisateur aime ; une playlist à règles peut être triée en Flow.

**Architecture:** `data/model/FlowEngine.kt` (pur, testé) porte tout le raisonnement : `FlowTrack` (identifiant, artiste, BPM, tonalité, énergie), coût de transition (`0,5 × Δbpm_rel + 0,35 × camelot/3 + 0,15 × |Δénergie|`, tolérance d'octave, pénalité 0,25 même artiste que l'un des deux précédents, 0,6 pour un titre sans données), parcours glouton depuis un titre de départ puis 2-opt borné à 2 000 échanges, arcs `STEADY` / `RISE` / `WAVE` (pénalité 0,3 sur les variations d'énergie à contre-sens ; `WAVE` bascule aux deux tiers), et `explain(from, to)` qui rend les trois faits affichés. Les surfaces adaptent leurs données en `FlowTrack` : `PlayerConnection` (les `MediaItem` après le courant, identifiés par leur position), `DailyMixEngine` (titres favoris / bien notés / écoutés depuis 90 jours, tous analysés), `RulePlaylistEngine` (titres filtrés). Le drapeau Flow vit **en mémoire** dans `PlayerConnection` (`FlowState` : arc, ordre précédent, instantané des identifiants de la file) et s'expose dans `PlayerUiState` (`flowActive`, `flowArc`, `flowReason`) ; il tombe dès que la file change autrement que par Flow. Le réordonnancement passe par `MediaController.replaceMediaItems(currentIndex + 1, count, reordered)` : un seul événement de timeline, aucune coupure.

**Écarts assumés avec la spec §7 :**
- `flowActive` n'est **pas** persisté dans `PlaybackStateEntity` (pas de migration 18) : après un redémarrage du processus, la file restaurée est encore dans l'ordre Flow mais l'explication et l'état du bouton repartent à zéro. Un appui sur « Flow » recalcule.
- Il n'existe pas de section « À suivre » dans `NowPlayingScreen` (la file se présente par « File · N » dans la barre d'actions). La ligne « Pourquoi ce titre : … » s'affiche sous la barre d'actions du lecteur, et le sous-titre de la ligne « Flow » de la feuille de la file reprend la même explication.
- `RulePlaylistRules` ne gagne pas de champ `flow` : le tri `SmartSort.FLOW` suffit (ordre Flow après filtrage, `descending` ignoré). Le JSON des playlists existantes reste lisible sans migration.
- « Caler sur l'énergie » (étape 6) s'applique déjà à toute file, Flow ou non : `DualDeckScheduler` lit `outroMs` / `introMs` dès que le réglage est actif. Le Flow n'ajoute pas de condition (restreindre au Flow aurait régressé l'étape 6) ; aucun câblage service ↔ UI n'est nécessaire pour `flowActive`.
- Activer Flow désactive le mode aléatoire : un ordre calculé n'a pas de sens sous `shuffleModeEnabled`.
- Un titre « sans données » est un titre sans BPM ou sans tonalité (`TrackTraits.hasBpm && hasKey` faux, ou non analysé). Au moins deux titres après le courant doivent avoir des données, sinon le bouton signale « Analyse le son de ta bibliothèque d'abord » (canal d'erreurs existant) et ne touche pas la file.
- La passe 2-opt est sautée au-delà de 400 titres après le courant (la file dépasse rarement 200 ; le glouton seul reste O(n²)).
- Pas de `CamelotTest` séparé : `KeyNames.distance` existe depuis l'étape 5 et `FlowEngineTest` couvre les trois distances demandées (8A–9A, 8A–8B, 8A–3A).

**Spec:** `docs/superpowers/specs/2026-11-24-synxio-6.0-flow-design.md` §7 ; prérequis : étapes 5 (`v5.15.0`, traits) et 6 (`v5.16.0`, `CrossfadePlayer`) livrées.
