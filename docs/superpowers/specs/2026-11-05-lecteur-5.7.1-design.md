# Lecteur 5.7.1 — flux de position, gestes, haptique

*Sous-lot 5.7.1 du séquencement de `docs/AUDIT_EVOLUTION_2026-11.md` (§6). Propositions I6, I10 et P7. Base : branche `dev-5.5` après la 5.6.1 (commit `29b49c6`). Date : 5 novembre 2026.*

## Objectif

Rendre le lecteur plus fluide et plus « premium » sans refonte : la position de lecture cesse de faire recomposer toute l'interface, le lecteur plein écran se manipule au doigt et au retour prédictif, le mini-lecteur gagne des balayages, et les interactions clés donnent un retour tactile cohérent.

## Constat vérifié dans le code

- `PlayerUiState` (`playback/PlayerConnection.kt`) porte `positionMs` et `bufferedMs`, échantillonnés toutes les 250 ms par `tickPosition()`. `SynxioRoot` collecte `playerState` à la racine (`SynxioRoot.kt:271`) et `NowPlayingScreen` collecte l'état entier (`NowPlayingScreen.kt:178`) : toute l'arborescence se recompose quatre fois par seconde pendant la lecture.
- Le lecteur plein écran est un `AnimatedVisibility` piloté par un booléen `playerExpanded`, avec un `BackHandler` simple (`SynxioRoot.kt:325`, `:443`). Aucun geste de fermeture, aucun retour prédictif, bien que `android:enableOnBackInvokedCallback="true"` soit déjà déclaré et que `activity-compose` 1.13 fournisse `PredictiveBackHandler`.
- `MiniPlayer` (`ui/components/MiniPlayer.kt`) gère déjà, par `detectDragGestures`, le balayage horizontal (suivant/précédent, carte qui suit le doigt avec résistance) et le balayage vers le haut (ouverture décidée au relâcher, sans suivi continu). Aucun balayage vers le bas, aucun retour haptique.
- `sharedPlayerElement` (`ui/components/SharedTransitions.kt`) exige un `AnimatedVisibilityScope` fourni par `LocalPlayerAnimatedScope` : le conteneur `AnimatedVisibility` du lecteur doit rester pour que la pochette voyage entre mini-lecteur et plein écran.
- Le seul retour haptique de l'app est dans `Reorderable.kt` (glisser-déposer).
- Les animations réduites viennent de `LocalReduceMotion` (`ui/theme/Tokens.kt:150`), alimenté par le réglage système.

## 1. Flux de position séparé (I6)

### 1.1 Modèle

Nouveau type dans `playback/PlayerConnection.kt` :

```kotlin
data class PlayerPosition(
    val positionMs: Long = 0L,
    val bufferedMs: Long = 0L,
    val durationMs: Long = 0L,
) {
    val progress: Float get() = if (durationMs > 0) (positionMs.toFloat() / durationMs).coerceIn(0f, 1f) else 0f
    val buffered: Float get() = if (durationMs > 0) (bufferedMs.toFloat() / durationMs).coerceIn(0f, 1f) else 0f
}
```

`PlayerConnection` expose `val position: StateFlow<PlayerPosition>`. `PlayerUiState` perd `positionMs`, `bufferedMs` et la propriété calculée `progress` ; il conserve `durationMs`, utile aux affichages statiques (durée totale, file d'attente).

### 1.2 Production

`tickPosition()` écrit dans `_position` au lieu de `_state`, à la même cadence qu'aujourd'hui : 250 ms en lecture, 1 000 ms en pause, `LOOP_TICK_MS` quand une boucle A-B est active. La boucle A-B continue de lire `loopStartMs` / `loopEndMs` dans `_state` et de replacer la position dans `_position`. `seekTo()` et `seekBy()` écrivent la position cible dans `_position` immédiatement, sans attendre le prochain échantillon. Au changement de morceau, `_position` est remis à zéro avec la nouvelle durée dès que `Player.Listener` la connaît.

### 1.3 Consommateurs

Seuls les composants qui affichent la position collectent `position` :

| Composant | Aujourd'hui | Après |
|---|---|---|
| `SeekBar` (`NowPlayingScreen`) | `state.positionMs` | `viewModel.position.collectAsStateWithLifecycle()` à l'intérieur du composant |
| Paroles synchronisées (`LyricsViewModel.adjustedPosition`) | `state.positionMs` passé en paramètre | la vue des paroles collecte `position` elle-même |
| Chapitres de livre (`liveBook` dans `NowPlayingScreen`) | `remember(..., state.positionMs)` | `remember(..., position.positionMs)` dans un sous-composable dédié |
| Bouton signet (`bookmarkAt`) | `state.positionMs` | `viewModel.position.value.positionMs` au moment du clic |
| `MiniPlayer` barre fine | `state.progress` | paramètre `progress: Float` fourni par un sous-composable qui collecte `position` |
| `DriveModeScreen` | `s.positionMs` | collecte `position` |
| Widget (`WidgetState`) | déjà alimenté par `PlaybackService`, hors UI Compose | inchangé |

`AppViewModel` expose `val position: StateFlow<PlayerPosition> = player.position`. Les écrans qui n'affichent pas la position (`SynxioRoot`, en-tête du lecteur, file d'attente, commandes) ne se recomposent plus au rythme de l'échantillonnage.

### 1.4 Tests

- `PlayerPositionTest` : `progress` et `buffered` bornés dans [0, 1], 0 quand la durée est inconnue.
- Les tests existants de `PlayerUiState` (s'il y en a) sont adaptés : plus de `positionMs`.

## 2. Gestes du lecteur (I10)

### 2.1 Un seul état d'expansion

`playerExpanded: Boolean` est remplacé par un état continu `expansion ∈ [0, 1]` (0 = mini-lecteur, 1 = plein écran), porté par un `Animatable<Float>` dans `SynxioRoot`. L'`AnimatedVisibility` du lecteur plein écran reste (il fournit le `AnimatedVisibilityScope` de la pochette partagée) mais avec `EnterTransition.None` / `ExitTransition.None` et `visible = expansion > 0` : le mouvement vient d'un `graphicsLayer` piloté par `expansion`. Cet état pilote :

- le décalage vertical (`translationY = (1 − expansion) × hauteur`) et l'alpha du lecteur plein écran ;
- l'alpha du mini-lecteur (`1 − 2 × expansion`, effacé à partir de 0,5) ; il est retiré de la composition quand `expansion = 1` ;
- la pochette partagée (`SharedTransitionLayout`, déjà en place), qui s'anime à l'apparition et à la disparition du lecteur avec son propre ressort.

Quatre sources font varier `expansion` :

1. **Tap sur le mini-lecteur** : animation vers 1 (ressort `Motion.spatial`).
2. **Balayage vers le haut sur le mini-lecteur** : `expansion` suit le doigt (déplacement rapporté à la hauteur de l'écran) ; au relâcher, la décision ouvrir/fermer vient de `PlayerSheetState.settle()`.
3. **Balayage vers le bas sur le lecteur plein écran** : même suivi, depuis 1 vers 0. Le geste n'est capté que s'il commence dans les 65 % supérieurs de l'écran (pochette, titre, scène) : la barre de progression et les commandes, en bas, ne le déclenchent jamais. Une liste défilable (paroles, file) consomme le geste tant qu'elle peut défiler ; le parent ne reçoit que le reste.
4. **Retour prédictif** : `PredictiveBackHandler(enabled = expansion > 0f)` ; `BackEventCompat.progress` pilote `expansion = 1 − progress × 0,4` (aperçu partiel, le lecteur ne descend que de 40 % pendant le geste système) ; `onBackCancelled` revient à 1 ; la fin du geste anime vers 0.

`BackHandler(enabled = playerExpanded)` disparaît, remplacé par le `PredictiveBackHandler`. Sur Android 13 sans l'option développeur, `PredictiveBackHandler` se comporte comme un retour classique : fermeture animée.

### 2.2 Décision pure : `PlayerSheetState`

Objet pur dans `ui/components/PlayerSheetState.kt`, testé sur la JVM :

```kotlin
class PlayerSheetState(private val screenHeightPx: Float) {
    /** Convertit un déplacement vertical cumulé (px, positif vers le bas) en expansion à partir d'un point de départ. */
    fun dragTo(startExpansion: Float, dragPx: Float): Float
    /** Décide la cible au relâcher : 1f (ouvert) ou 0f (fermé). */
    fun settle(startExpansion: Float, expansion: Float, velocityPxPerSec: Float): Float
    /** Vrai si un balayage vers le bas peut commencer à cette hauteur relative (0 = haut de l'écran). */
    fun canStartDrag(startYFraction: Float): Boolean
    companion object {
        const val OPEN_THRESHOLD = 0.3f      // part de la hauteur à parcourir sans vélocité
        const val FLING_VELOCITY = 1_200f    // px/s : au-delà, la direction du geste décide
        const val DRAG_ZONE = 0.65f          // zone de départ du balayage vers le bas
    }
}
```

Règles : si `|velocity| ≥ FLING_VELOCITY`, la direction décide (vers le bas ferme, vers le haut ouvre) ; sinon, en partant de 0 on ouvre si `expansion ≥ 0,3`, en partant de 1 on ferme si `expansion ≤ 0,7`.

### 2.3 Balayages du mini-lecteur

- **Horizontal** : conservé tel quel (carte qui suit le doigt, résistance au-delà de `SwipeThreshold`, `AnimatedContent` qui fait glisser pochette et titre). Ajout : un `tick()` haptique quand le changement est validé.
- **Vertical vers le haut** : devient continu. Le déplacement est rapporté à `SynxioRoot` (`onExpandDrag(totalYPx)` / `onExpandRelease(velocityPxPerSec)`), qui fait suivre `expansion` et décide par `PlayerSheetState.settle(0f, …)`. Sous animations réduites, le comportement actuel (décision au relâcher) est conservé.
- **Vertical vers le bas** : nouveau. Au-delà de 40 % de la hauteur de la carte, ou vélocité vers le bas ≥ `FLING_VELOCITY`, `onDismiss` met en pause et masque le mini-lecteur ; une snackbar « Lecture arrêtée » avec action « Annuler » relance la lecture au même point (durée : celle des messages à action de l'app). Le mini-lecteur réapparaît dès que la lecture reprend, quelle qu'en soit la cause.
- Les boutons existants restent : aucun geste n'est le seul chemin (accessibilité, principe déjà posé dans le KDoc de `MiniPlayer`).

Précédence des gestes dans `MiniPlayer` : décidée au premier mouvement dépassant le `touchSlop`, vertical si `|dy| ≥ |dx|`, sinon horizontal ; le geste garde son axe jusqu'au relâcher.

### 2.4 Animations réduites

Quand `LocalReduceMotion` est vrai : pas de suivi continu (le geste est reconnu au relâcher seulement), transitions en fondu comme aujourd'hui, et le retour prédictif ferme sans aperçu. Les décisions (`settle`, ancres) restent les mêmes.

### 2.5 Tests

- `PlayerSheetStateTest` : `dragTo` borné et proportionnel ; `settle` avec vélocité positive/négative au-dessus du seuil ; sans vélocité de part et d'autre de 0,3 et 0,7 ; départ à 0 et à 1.
- Pas de test instrumenté : la logique de geste Compose est vérifiée sur l'appareil (étape finale du plan).

## 3. Haptique musicale (P7)

### 3.1 Vocabulaire

`ui/haptics/SynxioHaptics.kt` :

```kotlin
interface SynxioHaptics {
    fun tap()      // lecture/pause, changement d'onglet
    fun confirm()  // cœur, ajout à la file, signet
    fun tick()     // changement de morceau par balayage, franchissement d'un seuil de geste
    fun release()  // fin de glissement de la barre de progression
}
val LocalSynxioHaptics = staticCompositionLocalOf<SynxioHaptics> { SynxioHaptics.None }
```

Implémentation `ComposeHaptics(hapticFeedback: HapticFeedback)` qui mappe : `tap` → `HapticFeedbackType.VirtualKey`, `confirm` → `Confirm`, `tick` → `SegmentTick`, `release` → `GestureEnd` (types disponibles depuis Compose UI 1.8, inclus dans le BOM 2026.09). `SynxioHaptics.None` ne fait rien. Aucune permission `VIBRATE` ajoutée : tout passe par `LocalHapticFeedback`, qui respecte le réglage système « Retour au toucher ».

### 3.2 Réglage

`Settings.hapticsEnabled: Boolean = true`, clé DataStore `haptics_enabled`, setter `setHapticsEnabled(value)`. Dans Réglages → Apparence, groupe « Mouvement et lumière » (à côté de « Réduire les animations »), une ligne « Retour haptique » avec interrupteur, sous-titre « Vibrations légères sur les commandes et les gestes ». `SynxioRoot` fournit `LocalSynxioHaptics` = `ComposeHaptics` si `hapticsEnabled`, sinon `None`.

### 3.3 Points d'appel

| Lieu | Événement | Appel |
|---|---|---|
| `NowPlayingScreen`, `MiniPlayer`, `DriveModeScreen` | lecture/pause | `tap()` |
| `NowPlayingScreen` | cœur, ajout à la file, signet | `confirm()` |
| `BottomBar` (`SynxioRoot`) | changement d'onglet | `tap()` |
| `MiniPlayer` | balayage horizontal validé | `tick()` |
| `MiniPlayer`, lecteur plein écran | franchissement du seuil ouvrir/fermer pendant le geste | `tick()` (une fois par franchissement) |
| `SeekBar` | `onValueChangeFinished` | `release()` |
| `Reorderable` | inchangé (déjà haptique) | — |

« Pulsation au tempo » est exclue de ce sous-lot : elle dépend de l'analyse BPM (N3, lot 6.2).

### 3.4 Tests

`SynxioHapticsTest` : un faux `HapticFeedback` enregistre les types reçus ; chaque méthode envoie le type attendu ; `None` n'envoie rien.
